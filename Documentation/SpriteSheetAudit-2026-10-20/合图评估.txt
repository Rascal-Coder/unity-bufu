Sprite sheet 与包体评估（2026-10-20）

检查对象
Assets/Resources 下全部 1,564 张 PNG；当前源图尺寸、透明边界、像素重复、导入设置、动态加载代码，以及最近一次成功交付的 Unity 构建日志。
此次为只读评估：没有修改图片、导入设置、加载器或 Windows 游戏包。新增文件仅为分析脚本、清单和本报告。

先说结论
可以合图，但不能把“减少图片文件数量”直接等同于“减少游戏包体”。
当前纹理在 Unity 构建日志中约为 445.5 MiB，占用户资源 96.0%；完整开发构建约 559.0 MiB。
PNG 磁盘大小、Unity 构建日志里的资源大小、GPU 内存和下载包体分别是不同指标。
以下当前体积均来自最近构建日志的逐资源近似值，单位 MiB；图集大小为离线矩形装箱模拟，未经重新构建验证。

包括 Back、Evolve、Challenge、Auction、世界名、商城商品名、三个商城页标题与侧边入口标签。
适合同一文字图集，也可以按商城/通用文字拆成两个图集。

因此这一组的包体收益主要来自尺寸与合适压缩，图集负责统一加载和批次。

建议继续独立的资源
三张 1024x1024 商城插画：diamond-vault-native-v2、no-ads-pass-native-v2、fragment-pack-native-v2，当前合计 12 MiB。
三张图都在实际代码中引用，不能当未使用资源移除。它们先独立评估缩至 512，再做平台压缩；单纯原尺寸带 padding 合入 2048 图集会造成明显浪费。
大背景、完整场景图和大面板：单独按分辨率、是否需要 alpha 和平台压缩优化。
Spine：已有自己的 atlas.txt，重新合并会涉及 atlas 及 UV，不作为第一批。
Art/Textures 中 60 张 VAT 纹理：运行时按 UV 与片段读取，保持现有结构。
UI/Textures 中字体与粒子等现有图集：保留专用结构，避免与普通 UI 混用。

当前加载方式需要配套处理
UI/UiPrefab.cs 中 UiAssets.LoadSprite 使用 Resources.Load<Texture2D> 再 Sprite.Create；其中 580 张 UI 图片的 PNG 尺寸与逻辑 SpriteMeta 尺寸不同，运行时 Pad 会创建恢复原尺寸的新纹理。
GameController.Purchases.cs 的 StoreIllustration 也直接按 CommerceArt 的 Texture2D 路径加载；按钮、商品卡片和底栏还会创建带 border 或局部区域的 Sprite。
只新增 SpriteAtlas 文件，无法自动替换这些 Texture2D 路径。
实施时应先增加 key -> atlas/subsprite 的统一查找，再保留原 pivot、逻辑大小、边界偏移、九宫格 border 与 Sprite.name；否则会失去原布局或合批收益。
成功迁移后，原散图应移到 Resources 外作为源素材，并解除其他构建依赖；不能让散图和图集一起保留在交付资源中。
Canvas UI 图集关闭旋转，预留至少 4px 间距与必要的边缘扩展；压缩后重点检查白字描边、金色边框与透明边缘。
可评估 Windows BC7；移动端另选支持的 ASTC 等格式。压缩体积与画质需要目标平台构建实测，不能套用同一组结果。

建议执行顺序
第一步：清理已证实重复的 Art/UI 构建资源。
第二步：用新字图与商城按钮做小范围图集加载验证，同时测试合适分辨率；这批素材独立、引用集中、回归路径清楚。
第三步：迁移道具与货币、常用 HUD 图标。
第四步：按动画族和页面逐批迁移特效与活动资源。
每步以同一构建模式比较完整交付体积与纹理体积，检查启动/切页/购包/拍卖/特效，并验证原有 UI 留白与点击区域。
